## 2. 项目定位

### 2.1 项目名称

AI Log Monitoring，定位为 AIOps 软件工程智能体平台，设计代号为 SE-Agent。

### 2.2 解决的问题

目标系统需要解决以下运维和研发问题：

- 日志、Docker、MySQL、Redis、RocketMQ、Git 和运行环境信息分散在不同系统中。
- 告警产生后，工程师需要人工跨多个工具收集上下文。
- 故障根因依赖个人经验，判断过程不可复用、不可审计。
- 修复建议、代码修改、验证和复盘之间缺少统一流程。

### 2.3 建设目标

长期目标是实现以下闭环：

```text
观测异常
  → 生成标准事件
  → 收集多源上下文
  → 分析根因
  → 生成修复计划
  → 执行修复
  → 验证修复结果
  → 人工/智能审查
  → 沉淀记忆并持续学习
```

当前项目尚未完成完整闭环，现阶段的实际能力主要集中在：

- 公共事件模型与内存事件总线
- Docker、MySQL、Redis、RocketMQ、RustFS 工具封装
- 日志和基础设施轮询采集
- 多源上下文构建
- 基于确定性规则的根因判断
- Dashboard 健康检查和 WebSocket 基础骨架
- Orchestrator 状态机骨架

## 4. 总体架构

### 4.1 架构形态

项目采用模块化单体架构：

- 所有业务模块以 Maven 子模块存在。
- `orchestrator` 是唯一 Spring Boot 启动入口。
- 其他模块是被 `orchestrator` 依赖引入的库模块。
- 所有模块使用 `com.ailog.<module>` 包前缀。
- Spring Boot 通过 `scanBasePackages = "com.ailog"` 扫描所有模块中的 Bean。
- 当前事件总线是 JVM 内存实现，不是 RocketMQ 分布式事件总线。

### 4.2 总体逻辑图

```text
┌───────────────────────────────────────────────────────────────┐
│                         orchestrator                          │
│       唯一 Spring Boot 入口 / 状态机 / 统一配置加载            │
└──────────────────────────────┬────────────────────────────────┘
                               │
        ┌──────────────────────┼──────────────────────┐
        ▼                      ▼                      ▼
┌───────────────┐     ┌────────────────┐     ┌──────────────────┐
│ observe-engine│     │ context-builder│     │ root-cause-engine│
│ 5 Collectors  │────▶│ 7 Providers    │────▶│ 5 Rules          │
│ 30s polling   │     │ ContextPackage │     │ RootCauseReport  │
└───────┬───────┘     └────────────────┘     └──────────────────┘
        │                         ▲                    │
        └──────────▶ EventBus ────┘                    ▼
              ┌────────────────────────────────────────────┐
              │             mcp-tool-center                │
              │ Docker / MySQL / Redis / RocketMQ / RustFS │
              └────────────────────────────────────────────┘

┌────────────────────┐       ┌─────────────────────────────┐
│ dashboard           │◀──────│ React 前端                  │
│ REST + WebSocket    │       │ 当前为 Vite 脚手架           │
└────────────────────┘       └─────────────────────────────┘

后续目标：
RootCauseReport → planner → executor → validation → review → memory/learning
```

### 4.3 架构原则

#### 模块化单体优先

第一阶段不拆分微服务，降低服务发现、网络调用、分布式事务和部署复杂度。

#### 事件驱动解耦

观测模块只负责发布事件，下游模块通过 EventBus 消费事件。后续可以在不改变业务接口的前提下替换为 RocketMQ 或其他消息实现。

#### 确定性优先

根因分析优先使用可测试、可解释的规则；LLM 只作为后续增强，不作为第一阶段的唯一判断依据。

#### 失败隔离

Collector、Provider 和 Rule 都应尽量做到单点失败不阻断其他流程，并提供可观测的错误信息。

#### 安全可控执行

未来 Executor 涉及代码修改、命令执行、容器重启、部署等高风险操作，必须设计审批、权限、回滚和审计机制。

## 6. 模块开发大纲

### 6.1 common

#### 职责

定义所有模块共享的事件、严重程度、事件总线和通用响应模型。

#### 已完成能力

- `Event`：事件 ID、类型、服务、异常、消息、时间、来源、严重程度、扩展 payload。
- `EventType`：定义 12 种事件类型。
- `Severity`：定义事件严重程度。
- `EventBus`：支持发布、按类型订阅、全局订阅。
- `SimpleEventBus`：基于并发集合的 JVM 内存实现。
- `Result<T>`：统一成功和错误响应包装。

#### 未完成能力

- RocketMQ 持久化事件实现。
- 事件存储、去重和重放。
- 事件 schema 版本管理。
- 事件追踪 ID、关联 ID 和幂等键规范。
- EventBus handler 异常的统一记录与指标。

#### 后续验收标准

- 可以发布事件并被多个订阅者消费。
- 一个订阅者异常不会阻断其他订阅者。
- 事件字段和序列化格式有稳定契约。
- 至少覆盖发布、订阅、异常隔离和并发场景测试。

### 6.2 mcp-tool-center

#### 职责

将 Docker、MySQL、Redis、RocketMQ 和 RustFS 的基础设施操作封装为 Spring AI MCP 工具。

#### 已完成能力

- `DockerTool`：`ps`、`logs`、`restart`、`inspect`。
- `MysqlTool`：`query`、`tables`、`indexes`、`locks`、`slowSql`。
- `RedisTool`：`keys`、`ttl`、`memory`、`clusterInfo`、`monitor`。
- `MqTool`：`consumers`、`lag`、`retry`、`deadLetter`。
- `RustfsTool`：`list`、`get`、`put`、`delete`。
- 使用 `@Tool` 注解暴露工具方法。

#### 未完成或需要整改的能力

- 工具参数校验和权限控制。
- MySQL 查询仅允许 SELECT 的强制校验。
- 表名、Key、对象路径的输入校验。
- Docker 重启、RustFS 删除等危险操作的审批控制。
- 统一异常类型和结构化返回值。
- RocketMQ Admin 客户端连接池化或共享 Bean。
- 工具调用审计、超时、限流和指标。
- MCP 端点的认证和跨域安全配置。

#### 后续验收标准

- 正常服务可访问时每个工具均能得到可解释结果。
- 外部服务不可用时返回结构化错误，不导致 Spring 应用退出。
- 查询型工具禁止执行写操作。
- 高风险工具有权限校验、审计记录和明确的失败结果。

### 6.3 observe-engine

#### 职责

周期性访问日志和基础设施，生成统一 `Event` 并发布到 EventBus。

#### 已完成能力

- `EventCollector` 接口。
- `ObserveEngineService` 统一遍历 Collector 并发布事件。
- `ObserveScheduler` 使用 `fixedDelay` 调度，默认 30 秒。
- `LogCollector` 扫描日志目录中的 `*.log` 文件。
- `DockerCollector` 读取容器状态。
- `MysqlCollector` 读取慢查询进程。
- `RedisCollector` 读取内存信息。
- `MqCollector` 检查默认消费者组重试队列。

#### 未完成能力

- `LOG_WARN` Collector。
- `METRIC_ALERT` Collector。
- `TRACE_ANOMALY` Collector。
- `DEPLOY_EVENT` Collector。
- `K8S_EVENT` Collector。
- `CI_FAILURE` Collector。
- `CONFIG_CHANGE` Collector。
- 日志采集路径的正式配置和启动校验。
- Collector 健康状态、连续失败计数和熔断。
- Collector 结果去重、事件聚合和告警抑制。
- Cron 表达式调度能力。
- 采集指标、延迟和失败率监控。

#### 重点整改项

1. Docker 查询需要明确是否包含停止容器，否则无法可靠捕获退出事件。
2. Docker 状态追踪需要真正比较前后状态，避免每轮重复告警。
3. Redis 不能仅根据 `used_memory_rss` 字段存在就触发故障，应比较阈值或配置。
4. MQ 不能通过字符串结尾判断数字是否为零，应解析队列数量。
5. 日志文件轮转、截断、编码和多行异常堆栈需要专项测试。

#### 后续验收标准

- 新增异常在一个调度周期内生成一次事件。
- 同一异常在未恢复前不会无限重复告警。
- Collector 单独失败不会影响其他 Collector。
- Collector 连续失败可被 Dashboard 或日志明确发现。
- 采集结果具有时间、来源、服务和扩展 payload。

### 6.4 context-builder

#### 职责

围绕事件采集多源环境信息，输出供根因分析使用的 `ContextPackage`。

#### 已完成能力

- `ContextProvider` 接口。
- `ContextData` 成功/失败模型。
- `ContextPackage` 事件上下文容器。
- Docker、DB、Redis、MQ、Git、Code、Env 七个 Provider。
- Provider 失败隔离。
- `ContextData` 已存在 Key 常量和类型转换访问器。

#### 当前实际调用关系

源码中 `ContextBuilderService` 负责显式执行 `build(event)`；当前根因引擎的事件处理逻辑会调用该方法。Context Builder 本身没有独立的 EventBus 订阅适配器。

#### 未完成能力

- 独立的 EventBus 自动触发适配器。
- ContextPackage 持久化、缓存和过期策略。
- 完整上下文输出消费链路。
- 全限定类名到源码路径的真实堆栈解析。
- Trace 链路数据和跨服务调用关系。
- Provider 超时、重试和限流。
- ContextData 的统一 schema 和版本管理。

#### 后续验收标准

- 每类事件都能得到明确的 Provider 选择策略。
- Provider 失败时仍能返回完整 ContextPackage。
- 上下文数据包含来源、采集时间和失败原因。
- Code Provider 能从标准 Java 堆栈定位类和行号。
- 重复事件可以复用短时间内有效的上下文快照。

### 6.5 root-cause-engine

#### 职责

基于 ContextPackage 执行确定性根因判断，生成 `RootCauseReport`。

#### 已完成能力

- `RootCause` 枚举。
- `RootCauseReport` 模型。
- `RootCauseAnalyzer` 规则接口。
- Code Defect、Resource Exhaustion、Config Error、DB Performance、Dependency Failure 五条规则。
- 规则优先级排序。
- 规则启用/禁用配置。
- 第一层直接根因优先返回。
- 第二层影响或症状类根因按证据数量选择。
- 源码中 `RootCauseEngineService` 已通过 `@PostConstruct` 注册全局 EventBus handler。
- 源码中规则已使用 `ContextData.get(key, Class)` 类型访问器。

#### 未完成能力

- 多事件关联和 `EventGroup`。
- 同一服务/时间窗口/指纹的聚合。
- 规则从硬编码关键词升级为可管理策略。
- LLM 辅助分析。
- 根因报告持久化和查询。
- 根因分析结果推送到 Dashboard。
- 规则命中率、误报率和人工反馈闭环。

#### 文档与源码差异说明

当前 `AGENTS.md` 的未完成目标中仍写有“root-cause-engine 未接入 EventBus”和“证据链类型不安全”。经源码核验：

- EventBus 全局订阅已经存在。
- `ContextData` 已提供类型安全访问器，规则也已使用。

因此这两项不应再作为源码实现缺口，但应作为文档同步问题记录；剩余的多事件关联、硬编码规则和 LLM 能力仍未完成。

#### 后续验收标准

- 对已支持事件类型可以返回确定性根因或 UNKNOWN。
- 报告包含事件 ID、根因、证据、受影响服务和建议动作。
- 规则异常不会影响其他规则。
- 规则配置改变后无需修改代码即可启停和调整优先级。
- 多事件关联结果可解释，并能追溯原始事件。

### 6.6 planner

#### 当前状态

空骨架，仅有配置和模块描述，没有修复计划生成逻辑。

#### 目标能力

- 输入 `RootCauseReport` 和相关 ContextPackage。
- 识别修复类型：配置、代码、依赖、资源、数据库、运维操作。
- 生成有序修复步骤。
- 标识风险、前置条件、影响范围和回滚方式。
- 区分建议操作、可自动执行操作和必须人工审批操作。

#### 建议输出模型

```text
RepairPlan
  - planId
  - eventId
  - rootCause
  - riskLevel
  - preconditions[]
  - steps[]
  - validationChecks[]
  - rollbackSteps[]
  - approvalRequired
```

#### 未完成验收项

- 尚无接口、模型、实现和测试。
- 尚未与 RootCauseEngine 建立调用关系。

### 6.7 executor

#### 当前状态

空骨架，没有代码修改、Git 操作、命令执行或部署实现。

#### 目标能力

- 创建隔离工作区。
- 执行 Git checkout 或分支操作。
- 应用受控代码修改。
- 执行单元测试、构建和静态检查。
- 执行可批准的 Docker、配置或基础设施动作。
- 记录每一步输入、输出、操作者和时间。
- 失败时执行回滚或暂停。

#### 安全要求

- 默认只读。
- 命令白名单。
- 工作区隔离。
- 高风险动作人工审批。
- 超时和资源限制。
- 全量审计。
- 修改前后差异保存。

#### 未完成验收项

- 尚无执行接口和实现。
- 尚无权限、审批、回滚和审计能力。

## 9. 分阶段开发路线

### 阶段 0：工程基线与安全清理

#### 目标

建立可重复构建、可追踪变更、可安全运行的工程基础。

#### 工作项

- 初始化或恢复 Git 仓库。
- 固定 Java、Maven、Node、pnpm 版本。
- 增加构建说明和环境检查脚本。
- 将 `application.yml` 中的明文凭据迁移为环境变量。
- 增加 `.env.example`，不提交真实凭据。
- 建立 CI 基线：后端编译、后端测试、前端 typecheck、前端 lint、前端 build。
- 增加依赖漏洞扫描和敏感信息扫描。

#### 验收标准

- 新环境可以按照文档完成依赖安装。
- 不需要修改源码即可配置外部服务。
- CI 能明确报告每个检查的成功或失败。

### 阶段 1：公共模型与事件可靠性

#### 目标

稳定 Event、EventBus、Result 和事件契约。

#### 工作项

- 增加事件唯一性、关联 ID、幂等键。
- 增加事件序列化测试。
- 增加 EventBus 并发和异常隔离测试。
- 设计内存总线与 RocketMQ 总线的统一接口。
- 增加日志、指标和 handler 错误记录。

#### 依赖

依赖 `common`，不依赖业务模块。

### 阶段 2：MCP 工具层安全与稳定性

#### 目标

让基础设施工具具备可控、可审计、可诊断的访问能力。

#### 工作项

- MySQL 查询只允许 SELECT。
- 对表名、Key、对象路径、容器 ID 做校验。
- 工具方法返回结构化结果或统一错误协议。
- 增加超时、限流、重试和熔断。
- 对危险操作增加审批接口。
- 增加每个工具的单元测试和集成测试。

#### 验收标准

- SQL 注入测试失败，即输入不能突破 SELECT 限制。
- 外部服务关闭时应用仍能启动，调用返回可读错误。
- 所有危险动作都有审计信息。

### 阶段 3：观测引擎完善

#### 目标

从“能采集”提升到“低误报、可去重、可观测”。

#### 工作项

- 修正 Docker 状态检测。
- 实现状态变化去重。
- 修正 Redis 阈值判定。
- 修正 MQ 数值解析和消费者组配置。
- 增加日志 WARN 和日志多行异常处理。
- 增加 Collector 健康状态。
- 增加可配置 fixedDelay/cron。
- 增加失败重试与熔断。

#### 验收标准

- 每个 Collector 都有正常、异常、空结果和外部服务不可用测试。
- 同一故障不会在每个周期无限生成重复事件。
- Collector 状态可以被 Dashboard 查询。

### 阶段 4：上下文构建完善

#### 目标

形成稳定、可追溯、可复用的 ContextPackage。

#### 工作项

- 定义事件到 Provider 的选择矩阵。
- 增加独立 EventBus listener 或统一触发适配器。
- 完善 Java 堆栈解析。
- 接入 Git 变更与服务映射。
- 增加上下文缓存和过期策略。
- 增加 Provider 超时、重试、失败原因和指标。

#### 验收标准

- 一个事件可以得到完整 Provider 状态清单。
- Provider 失败不影响其他 Provider。
- ContextPackage 可以持久化或序列化。

### 阶段 5：根因分析增强

#### 目标

从单事件规则判断提升到可解释的多事件事故分析。

#### 工作项

- 实现 `EventGroup`。
- 按服务、时间窗口、事件指纹做关联。
- 实现 `EventCorrelationEngine`。
- 规则输入支持事件组和多份上下文。
- 把关键词和阈值抽为配置或规则定义。
- 保存根因报告。
- 增加人工确认和反馈。
- 设计 LLM 辅助分析，但保留规则兜底。

#### 验收标准

- 同一事故的多个事件可以形成一份关联报告。
- 报告能列出原始事件和证据来源。
- LLM 不可用时规则分析仍然可用。

### 阶段 6：Dashboard 后端与前端

#### 目标

让事件、根因、系统状态和工作流可视化。

#### 工作项

- 设计 REST API DTO。
- 增加事件和根因查询服务。
- 改造 WebSocket 为事件广播器。
- 前端建立路由、请求层和状态管理。
- 实现仪表盘、事件中心和根因页面。
- 实现错误、加载、空数据和断线处理。

#### 验收标准

- 前端可以看到真实健康状态和事件。
- 新事件可以实时推送。
- 根因报告可以查看证据和建议动作。

### 阶段 7：Planner 与 Orchestrator 串联

#### 目标

让根因报告转化为可执行、可审批的修复计划。

#### 工作项

- 定义 `RepairPlan`、`RepairStep`、`Approval`。
- 将 Orchestrator 改为按 Workflow ID 管理状态。
- 连接 CONTEXT、DIAGNOSE、PLAN 状态。
- 增加暂停、恢复、取消和失败恢复。
- 增加计划预览和人工审批。

#### 验收标准

- 一个事件可以创建独立工作流。
- 工作流状态可持久化和查询。
- 计划包含风险、前置条件、验证和回滚步骤。

### 阶段 8：Executor

#### 目标

在安全边界内执行修复动作。

#### 工作项

- 工作区隔离。
- Git 分支和变更管理。
- 命令白名单。
- 测试和构建执行。
- Docker/配置操作审批。
- 执行日志和差异保存。
- 失败回滚。

#### 验收标准

- 未审批的高风险动作无法执行。
- 每一步可重放或解释。
- 执行失败可以停止在安全状态。

### 阶段 9：Validation Engine

#### 目标

确认修复是否真正解决问题，避免只验证代码构建通过。

#### 工作项

- 定义验证检查模型。
- 接入 API、日志、指标、数据库、Redis、MQ 和容器检查。
- 支持修复前后对比。
- 支持超时、部分成功和无法判断。
- 将验证结果反馈给 Orchestrator。

#### 验收标准

- 每个修复计划都有明确验证标准。
- 验证失败能触发回滚或人工介入。
- 结果可在 Dashboard 查看。

### 阶段 10：Review、Memory、Learning、Knowledge Graph

#### 目标

形成审查、经验复用和持续学习能力。

#### 工作项

#### 验收标准

- 一次事故可以沉淀成可检索经验。

## 10. 推荐开发流程

### 10.1 单项功能标准流程

每个新功能都遵循：

```text
确认需求
  → 阅读相关模块和设计文档
  → 明确接口和数据模型
  → 编写实施计划
  → 先写失败测试
  → 实现最小功能
  → 运行单元测试
  → 运行模块测试
  → 运行全量构建
  → 代码审查
  → 更新文档
  → 验收并合并
```

### 10.2 后端开发流程

1. 确定模块边界和依赖方向。
2. 优先更新模型和接口。
3. 为正常、空值、异常和外部服务失败编写测试。
4. 使用构造器注入依赖。
5. Collector、Provider 和 Rule 保持单一职责。
6. 不在业务模块中直接绕过 MCP 工具层访问外部基础设施，除非明确属于本地 Git 或源码文件操作。
7. 所有错误都要记录来源、事件 ID、服务和失败原因。
8. 功能完成后更新模块状态和未完成清单。

### 10.3 前端开发流程

1. 先定义后端 API 契约和 TypeScript 类型。
2. 先实现页面状态模型，再实现视觉布局。
3. 页面必须有加载、空数据、错误和断线状态。
4. 统一封装 API 和 WebSocket，不在页面组件中散落请求逻辑。
5. 组件优先使用现有 shadcn/Tailwind 约定。
6. 完成功能后执行 typecheck、lint 和 build。

### 10.4 高风险操作流程

涉及以下操作时必须增加人工确认：

- 修改生产代码。
- 执行数据库写操作。
- 删除 RustFS 对象。
- 重启 Docker 容器。
- 修改配置并发布。
- 执行任意 Shell 命令。
- 触发部署或回滚。

## 13. 安全、可靠性和性能要求

### 13.1 安全

- 清理仓库中的明文凭据。
- MCP 工具按读写风险分级。
- 默认关闭高风险操作。
- SQL 采用白名单和参数化。
- Shell 命令采用白名单，不允许直接拼接用户输入。
- Docker、RustFS、数据库操作增加权限校验。
- API 和 WebSocket 增加认证授权。
- 所有修复动作记录审计日志。
- 事件和报告中的敏感数据脱敏。

### 13.2 可靠性

- 外部服务调用设置连接和执行超时。
- 失败重试必须有上限和退避。
- 连续失败触发熔断。
- 事件处理支持幂等。
- 任务状态支持持久化。
- 关键操作支持回滚。
- EventBus 不应静默吞掉所有异常而没有记录。

### 13.3 性能

- Collector 轮询不能阻塞调度线程过长。
- 上下文 Provider 可以并行采集，但要限制并发度。
- 日志读取必须避免重复扫描和无限读取。
- RustFS 和 Docker 日志输出要限制大小。
- 事件列表需要分页或流式查询。
- WebSocket 广播需要客户端隔离和背压策略。
- MQ Admin 客户端应避免每次调用创建连接。
